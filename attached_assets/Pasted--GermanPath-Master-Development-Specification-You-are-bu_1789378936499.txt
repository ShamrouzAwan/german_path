# GermanPath — Master Development Specification

You are building **GermanPath**, a production-ready German-learning web platform.

GermanPath is conceptually similar to YouTube + Coursera/Udemy, but focused entirely on German-language learning.

The project must be designed from the beginning for **low-cost deployment on shared hosting**, specifically a hosting environment that supports **PHP + SQLite** but does not provide a VPS, Python server, Node server, Docker, or continuously running background processes.

The project will initially be developed through Replit AI and may be moved between multiple Replit accounts. Every Replit account will connect the project to the same GitHub repository. Therefore:

* Never depend on hidden Replit-only project state.
* Never store essential project information only inside Replit.
* The GitHub repository must contain everything required to continue development.
* Keep the application portable and deployable to ordinary PHP shared hosting.
* Avoid paid services and unnecessary third-party subscriptions.
* Prefer PHP standard functionality and lightweight/open-source libraries when genuinely necessary.
* Do not introduce infrastructure that requires a VPS.
* Cloudflare Workers and Cloudflare R2 are allowed because they are external serverless services already used by the project.
* The frontend must remain lightweight enough for inexpensive shared hosting.

---

# 1. DEVELOPMENT METHODOLOGY

Build the application **modularly, one module at a time**.

Do NOT attempt to generate the entire finished application in one step.

At the beginning, inspect the repository and establish a clean project structure.

Then implement modules in a logical order, fully completing and testing each module before moving to the next.

Every meaningful development action must be recorded in:

```text
logs/development.log
```

The log must contain timestamps and clear descriptions of:

* module started
* files created
* files modified
* database migrations
* configuration changes
* tests performed
* bugs discovered
* bugs fixed
* security changes
* unfinished work
* deployment-related changes
* decisions that affect future development

Create and continuously maintain:

```text
project.md
```

`project.md` is the living master project document.

It must contain:

* project overview
* current architecture
* current module
* completed modules
* TODOs
* known issues
* deferred features
* security considerations
* database changes
* JSON/content schema changes
* Worker integration status
* deployment requirements
* production-readiness checklist
* exact next steps

Every Replit AI action must update `project.md` and `logs/development.log`.

Never mark something complete unless it has actually been implemented and tested.

If a feature cannot be completed during the current action, explicitly record it as incomplete rather than pretending it is finished.

# 9. CRITICAL STORAGE MODEL

The same course may exist across **multiple R2 accounts/buckets**.

Therefore NEVER design:

```text
course → one bucket
```

Instead:

```text
course
 ├── video 1 → storage A
 ├── video 2 → storage A
 ├── video 3 → storage B
 ├── video 4 → storage C
 └── video 5 → storage B
```

Storage must be specified at the media/content-item level.

Example:

```json
{
  "id": "b1-001",
  "title": "Infinitiv + zu",
  "storage": "b1-old",
  "video": "01 - B1 ｜ Lektion 1 ｜ Infinitiv + zu.mp4",
  "subtitle": "01 - B1 ｜ Lektion 1 ｜ Infinitiv + zu.srt",
  "thumbnail": "01.jpg"
}
```

The course itself must not be assumed to have only one storage location.

# 17. CLOUDFLARE R2 / WORKER INTEGRATION

A Cloudflare Worker already exists conceptually as:

```text
r2-video-worker
```

It is designed to support multiple R2 accounts.

The website must communicate with the Worker through a reusable PHP service.

Current conceptual API:

```text
POST /api/v1/media
```

Request:

```json
{
  "account": "b1-old",
  "bucket": "b1-old",
  "media": "lesson.mp4",
  "subtitle": "lesson.srt"
}
```

The Worker returns temporary signed URLs.

The PHP website must:

* authenticate to the Worker using a server-side secret
* never expose that secret to the browser
* validate all content metadata before requesting media
* handle Worker failures gracefully
* handle missing/expired URLs
* never save temporary signed URLs permanently in SQLite
* request them when needed

The Worker remains the secure media-access layer.

The browser ultimately receives temporary URLs and streams directly from R2.

Do not proxy large video files through Hostinger PHP.

Do not attempt to download entire videos through the PHP server.

        ↓

        ↓

        ↓

        ↓
